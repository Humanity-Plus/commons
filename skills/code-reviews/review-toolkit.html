AI review toolkit

The Review Toolkit

An AI review loop for your PRs and branches: a multi-lens reviewer that produces an HTML report, a fixer that safely resolves the findings, and a publisher that posts the review to GitHub. Works in Claude Code, Cursor, and any agent skills.sh supports. Part of the Humanity Plus Commons, MIT-licensed.

01 Install (one command)

Two ways in, two philosophies, pick one. Installing both leaves you with every review skill twice.

Option 1: skills CLI (any agent, editable files)

Works with Claude Code, Cursor, Codex, and most other coding agents. The CLI lists the skills; you pick which ones and which agents.

npx skills add Humanity-Plus/commons -g
npx skills add Humanity-Plus/commons --list # see every skill first
npx skills add Humanity-Plus/commons \
  --skill review-pr -g # take one specific skill
npx skills update # pull the latest later

The skills land as ordinary files you own and can edit; nothing updates behind your back.

Option 2: Claude Code plugin (managed bundle)

Claude Code only. Installs the whole toolkit as one plugin from this repo's marketplace.

claude plugin marketplace add Humanity-Plus/commons
claude plugin install review-toolkit@humanity-plus

Or inside a session: /plugin marketplace add Humanity-Plus/commons then /plugin install review-toolkit@humanity-plus.

Plugin skills are namespaced: invoke them as /review-toolkit:review-pr, /review-toolkit:review-fix, … Update later with claude plugin marketplace update humanity-plus.

CLI installs: global only

With the skills CLI, install globally (-g), never project-scoped into a repo you then review other people's PRs in, a malicious PR checkout could swap the skill files for its own copy that executes as you. The plugin lane installs globally by nature, so it's safe by default.

Prerequisites

bun renders the HTML report (curl -fsSL https://bun.sh/install | bash) and gh (GitHub CLI, brew install gh then gh auth login) is needed for PR mode and publishing. Local-branch review works without gh.

02 What gets installed

Six skills. Two carry the core know-how, three chain them into everyday workflows, one bootstraps the configuration. In Claude Code every skill is also invocable directly as a slash command, /review-pr, /review-fix, … with the CLI install, or namespaced (/review-toolkit:review-pr) with the plugin.

SkillRoleWhat it is
review-prcoreThe reviewer. Runs independent lenses as parallel subagents (optionally sharded by feature area on large diffs, with a seams lens for cross-area contracts), verifies findings with a skeptic pass, calibrates severities with an arbiter, and renders the HTML report. Report-only, never edits code.
resolve-reviewcoreThe fixer. Turns a findings file into an ordered fix plan, applies one scoped edit per finding on your own branch (every site in a grouped finding's locations list), validates with the repo's existing checks, and reports fixed / partial / skipped / failed.
review-fixworkflowReview + fix in one pass, results in chat (no HTML). The agent-friendly loop.
publish-reviewworkflowPost a previous review to the GitHub PR as one real review.
review-issuesworkflowFile non-blocking findings (readability, naming, soft conventions) as grouped, deduped review-debt GitHub issues for a scheduled fixer.
map-primitivessetupThe mapper. Bootstraps or refreshes docs/primitives.md + primitives.yaml, the machine-readable map of your system's building blocks that the review's primitives lens consumes, and reports drift (the same concept re-declared in multiple shapes).

How the pieces chain together:

/review-pr
lenses → verify → arbiter → findings.json + report.html
/resolve-review
plan → scoped fixes → validate → resolution table
/publish-review
findings → inline PR comments + review body

/review-fix is a shortcut that runs the first two steps back-to-back on your own branch in findings-only mode (full pipeline, no HTML).

03 Configure it for your repo

The toolkit works out of the box, but three repo-owned files are its real configuration, they're what turn a generic review into your review, and where great results come from.

FileFeedsWhat goes in it
REVIEW.mdrepo root every lens, the verify pass, and the verdict Everything a reviewer can't infer from a diff: repo facts (“auth isn't wired yet”, “PRs are stacked”, “these paths are generated”), what high severity means here, a do-not-report list (what CI already enforces), an always-check list of your invariants, which stack areas the scorecard should grade, soft style preferences, and optional model-tier overrides. Start from skills/review-pr/REVIEW.example.md. This file is what kills repeat false positives.
docs/conventions/one file per topic the conventions lens Your own written rules, short, citable, split per topic (react.md, typescript.md, testing.md, …). Every conventions finding cites the rule it violates, and no written rule means no finding, this is what keeps the lens from devolving into a generic style bot. AGENTS.md/CLAUDE.md and .cursor/rules/ are read too.
docs/primitives.yaml+ primitives.md for prose the primitives lens A machine-readable map of your system's building blocks: each primitive with the sources files that define it, the invariants it must keep, and what it relates to. This is how a review can tell whether a diff composes existing primitives, extends one, or quietly invents a new shape, the classic failure of agent-written code. Bootstrap it with the map-primitives skill.

REVIEW.md, the shape that works

The lenses look for these headings specifically:

# Review instructions
## What Important means here   ← your severity bar
## Do not report               ← CI-enforced, generated, historical
## Always check                ← your invariants, each citing its rule
## Stack                       ← areas the scorecard grades
## Repo facts                  ← what a diff can't tell a reviewer
## Style                       ← soft preferences (low/nit)
## Review roles                ← optional model-tier overrides

Point it at your convention docs (“Web UI → react.md, backend → convex.md”) so lenses read the right files fully before reviewing. Two references ship with the skill: REVIEW.example.md is the skeleton to copy, and REVIEW.worked-example.md is a sanitized real one from a production app, what yours should grow toward.

primitives.yaml, one entry

primitives:
  - id: order
    area: data
    name: Order
    sources: [src/db/schema.ts, src/orders/]
    invariants:
      - Status only moves forward; cancel is a
        status, not a delete.
      - Totals are derived on write, never
        recomputed in the UI.
    relates_to: [customer, invoice]

sources is how changed file paths map onto primitives; a directory matches everything under it. List the primitive's shape, values, derived vocabulary, and the guards that enforce it — not files that merely consume it. Keep ids stable, and update the map in the same PR that changes or introduces a primitive.

Generated, then curated

All three files can be drafted by an agent: run /map-primitives to bootstrap the primitives map, and ask your agent to draft REVIEW.md (from REVIEW.example.md) and to distill docs/conventions/ from the patterns actually in your codebase. But treat every draft as a draft, these files are trusted context: a wrong “repo fact” suppresses real findings, and a stale rule grades new code against a dead convention. Read every line, prune what's wrong, and keep them living: add rules as they prove out, delete rules that stop pulling their weight.

Trust boundary & compatibility

In PR mode, REVIEW.md, the convention docs, and the primitives map are read from the base branch only, a PR can never rewrite the ruler it's measured with. REVIEW.md is deliberately the same file Anthropic's Claude Code Review reads, so one committed file drives both reviewers with no duplication. Keep it self-contained, neither tool expands @-imports.

04 How a review runs

One orchestrator, several independent perspectives, then skepticism and calibration.

Phase 1
triage
feature areas, risk map, interfaces, decides whether to shard
Phase 2
lenses
parallel subagents; sharded + seams on large diffs; optional holistic
Phase 3
verify
skeptic pass per finding, refute / confirm / downgrade
Phase 3.5
arbiter
regrade, group swarms, fold past the report budget
Phase 4
render
findings.json → report.html (skipped in findings-only)

Lenses

LensQuestion it answersWhen
triageWhat changed, grouped by feature area and risk?always first
first-fiveThe 5 things automated changes get wrong (errors, input, external calls, mutations, deps)always
conventionsRepo rules, stack idioms, sibling precedent + per-area scorecardwhen convention docs exist
warmNew/upgraded deps: Worth it, Alive, Right-sized, Maintained?deps only
zombiesMissing high-value tests (Zero / One / Many / Boundaries / Interface / Exceptions / Simple)always
preflightWhat must happen to deploy safely?always
intentDoes the diff match what the change claims to do (PR body, linked issues, spec files)?when a spec source exists
seamsDo the sides of every contract the diff crosses still fit together?when triage finds interfaces
primitivesWhat did the change do to the system's primitives (composes / extends / adds), and did it invent shapes outside the map?repo has primitives.yaml

Adaptive sharding

Diffs over shard-threshold changed lines (default 400) shard first-five, zombies, and conventions, one subagent per (lens × feature area). warm / preflight / intent stay whole-diff. Small PRs are untouched.

Severity arbiter

After verify, one pass regrades severity relatively, collapses 3+ same-class findings into one card with a locations list, and folds findings past the report budget (default 15) into a collapsed More findings section, never drops.

Holistic comparison (optional)

Pass holistic to also run a whole-diff generalist in parallel with Phase 2. Overlap stats land in a Holistic comparison card, holistic-only findings flag gaps in the lens decomposition. Off by default; an eval harness, not part of the everyday loop.

Role-based models

Subagents fill roles (triage, lens, seams, verify, arbiter, holistic) mapped to tiers (fast / balanced / strongest, resolved against whatever the host tool offers. No hardcoded model ids. Override per repo in REVIEW.md → ## Review roles.

05 Skill reference

Type / in the chat and pick the skill; anything you type after it becomes the argument. In agents without slash invocation, ask for the skill by name ("use review-pr on PR 482").

/review-pr

read-only

The full review. Produces review-report/findings.json (source of truth) and review-report/report.html, verdict, severity donut, risk heatmap, conventions scorecard, test-gap matrix, preflight checklist, plus (when applicable) grouped findings, a folded More findings section, and a Holistic comparison card. Ends with a short chat summary: verdict, counts, top 3 findings.

  • /review-pr current branch vs main
  • /review-pr 482 that PR number (fetched with gh)
  • /review-pr https://github.com/…/pull/482 a PR URL
  • /review-pr feature/wbs-tree a branch vs its base
  • /review-pr 482 shard-threshold=250 shard earlier than the default 400 lines
  • /review-pr 482 budget=20 keep more findings above the fold
  • /review-pr 482 holistic also run the whole-diff generalist comparison
  • /review-pr 482 context=docs/review.md use a non-default context file
  • /review-pr 482 no-report findings-only: full pipeline, findings.json, no HTML and no fix phase, review in a fresh unbiased session, then fix later with /resolve-review in the worktree that has the branch

/review-fix

writes code

The fast local loop, and the command to point agents at. Runs the same full review in findings-only mode (pipeline through arbiter, no HTML, no browser), then immediately fixes what's fixable on the current branch. Reports a resolution table straight to chat, plus a "over to you" list for things only a human can close. Never commits by itself.

  • /review-fix current branch vs main, fix in place
  • /review-fix feature/x review + fix that branch

/resolve-review

writes code

The second half, run separately: consume an existing review-report/findings.json (from a prior /review-pr), fix the selected findings, validate each fix with the repo's existing typecheck/lint/tests, and revert anything that breaks them. Grouped findings fix every site in locations[]; folded findings sit below the default threshold (include them only on explicit request).

  • /resolve-review default set, verified findings at medium+
  • /resolve-review high only high severity and above
  • /resolve-review conventions only one lens / feature area / specific finding ids

/publish-review

posts to GitHub

Turn a previous PR-mode review into one real GitHub review: findings anchored in the diff become inline file:line comments, everything else folds into the review body. Always dry-runs first and shows you exactly what will be posted, nothing goes out without your confirmation.

  • /publish-review inline comments for all anchorable findings
  • /publish-review gist also host the HTML report as a secret gist and link it
  • /publish-review medium only medium+ inline; the rest in the body
  • /publish-review body-only one summary comment, no inline comments

/review-issues

posts to GitHub

The review-debt lane. Files the review's non-blocking findings (low/nitpick, readability, naming, soft conventions) as GitHub issues so they get fixed later instead of dying with the report: one issue per defect class (never per nitpick), fingerprint-deduped across runs so re-reviews never re-file tracked debt, labeled review-debt + category. A scheduled fixer (e.g. the issue-fixer routine) drains them on clean runs. Confirms before creating; severity policy unchanged, this changes routing, not grading.

  • /review-issues file low + nitpick findings from the latest review
  • /review-issues medium widen the band to medium and below
  • /review-issues category=Readability only one category
  • /review-issues yes skip the confirmation (for routines that carry consent)

06 Agent automation

Three ways to make agents run the review loop before opening a PR, in increasing order of enforcement.

1 · Advisory

AGENTS.md rule

Works in Cursor, Claude Code, and cloud sessions, add one line to your project's AGENTS.md: “Before creating any PR, run /review-fix and include the resolution summary in the PR body.” A long session can still drift past it.

2 · Prompt

Routine prompts

For scheduled cloud agents, put the instruction in the routine's own prompt (“…then run /review-fix before filing the PR”). The prompt is the reliable channel there, don't count on the routine noticing a file mid-run.

3 · Hard gate

Claude Code hook

hooks/require-review-before-pr.sh blocks gh pr create until review-report/findings.json exists and is newer than the last commit. The harness enforces it, the agent can't skip it. See hooks/README.md.

Cursor vs the hook

Cursor does not execute Claude Code hooks, rely on the AGENTS.md rule there. The hook is a freshness check, not a quality check: it proves a review ran against the latest commit; whether remaining findings are acceptable is still your (and the agent's) call.

07 Example scenarios

Everyday situations and which command to reach for.

“I'm about to open a PR, check my work first”

You, on your own feature branch, before pushing.

  1. In the repo's chat, run /review-fix.
  2. The agent reviews your branch against main through the full pipeline (lenses → verify → arbiter), then fixes the verified findings in place, a null-check it missed, a convention violation with the rule it cites, a couple of missing edge-case tests.
  3. Read the resolution table in chat, skim git diff, and commit what you agree with.
Outcome: the obvious review comments are already resolved before a teammate ever sees the PR. No HTML report is produced, this is the quick loop.

“Review this PR properly before we merge it”

You, reviewing a teammate's pull request.

  1. Run /review-pr 482 (or paste the PR URL).
  2. The skill fetches the PR with gh, runs the lenses as parallel subagents (sharding + seams on large diffs), a skeptic pass verifies every finding, and the arbiter calibrates the report.
  3. Open review-report/report.html: verdict up top, risk heatmap by feature area, findings written like short teaching articles with diffs and diagrams.
  4. Happy with it? Run /publish-review gist, after a dry-run and your confirmation, the findings land on the PR as inline comments plus a summary review, with a link to the full report.
Outcome: a thorough, evidence-based review posted as one GitHub review, not a wall of bot comments. The review stays report-only; nothing on the PR branch is executed or edited.

“The review found 14 things, fix the important ones”

You, after a /review-pr on your own branch.

  1. Run /resolve-review high to only tackle high severity and above (or /resolve-review conventions to clear just the craft findings).
  2. The skill plans fixes ordered by severity, applies one minimal edit per finding (every site in a grouped finding), and runs the repo's existing checks after each, anything that breaks them is reverted and marked failed.
  3. Advisory items (deploy steps, PR-description mismatches) and folded findings come back as an explicit “over to you” list instead of being guessed at.
Outcome: a ledger of exactly what changed and what still needs a human, with git diff --stat. You stay in control of the commit.

“Make the agent refuse to open a PR without a review”

You, wiring Claude Code so the review loop can't be skipped.

  1. Add the pre-PR rule above to the project's AGENTS.md.
  2. Install hooks/require-review-before-pr.sh (project or global),see hooks/README.md.
  3. When an agent tries gh pr create without a fresh findings.json, the hook blocks it and tells the agent to run /review-fix first.
Outcome: every PR that goes out has been through the review → fix loop against the commit being filed. Cursor still relies on the advisory AGENTS.md rule.

“Do new dependencies and test coverage hold up?”

Anyone, these run automatically inside every review.

  1. Run /review-pr; no extra flags needed.
  2. The WARM lens audits each new/upgraded package: Worth it, Alive, Right-sized, Maintained securely, rendered as a table in the report.
  3. The ZOMBIES lens maps missing high-value tests (Zero / One / Many / Boundaries / Interface / Exceptions / Simple) per feature area, and /resolve-review tests can then write them.
  4. The preflight lens leaves you a checkbox list of deploy-time actions (migrations, config, secrets) right in the report.
Outcome: dependency risk, test gaps, and deploy steps are surfaced on every review without anyone remembering to ask.

08 Cursor vs Claude Code

Same skills, the installer can place them in both. Hooks are Claude Code only.

Cursor

Skills → ~/.cursor/skills/ (global install)

Skills are loaded automatically when the agent decides they're relevant; asking for one by name ("use review-pr on PR 482") is the reliable path. Pre-PR enforcement is advisory via AGENTS.md.

Claude Code

Skills → ~/.claude/skills/ (CLI install) or a managed plugin (plugin install)

Every skill is also a slash command: type /review-pr 482 (CLI install) or /review-toolkit:review-pr 482 (plugin) and the skill receives 482 as its argument. Optionally install the pre-PR hook for a hard gate.

If a workflow skill can't find its core skill

The workflow skills are thin, the logic lives in review-pr and resolve-review. If the agent says one of those isn't available, the fix is always the same: reinstall (npx skills add Humanity-Plus/commons -g, or reinstall the review-toolkit plugin) and restart the app.

09 Tips & safety

Read-only vs writes-code

/review-pr and /publish-review never edit the code under review. /review-fix and /resolve-review write code, run them only on a branch you own, never on a gh pr checkout of someone else's / a fork's PR. The commands enforce this themselves, but it's worth knowing why they refuse.

The diff is untrusted input

The reviewer treats everything in the diff as data, never instructions, comments or fixtures that try to steer the agent are ignored by design, and the HTML report sanitizes all diff-derived content. Keep command approval on in your editor, don't run reviews in an environment with cloud/publish tokens, and never npm install a checked-out PR. Details in skills/review-pr/README.md.

Teach it your repo once

Most repeat false positives trace back to missing configuration, not the pipeline. If the review keeps flagging the same non-issue, the fix is a line in REVIEW.md; if craft findings feel generic, the fix is a written rule in docs/conventions/. See Configure it for your repo.
